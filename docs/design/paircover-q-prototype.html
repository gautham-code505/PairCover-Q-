PairCover-Q dispatch console

A clickable version of the redesign. Pick a method and run it. Every number below was recorded from the project's own backend on 10 Oct 2026 and is replayed here; nothing is computed or invented in the browser. My changes to the original concept are listed under the console.

What I changed from the concept, and why

  1. Nothing is assigned before a run. The concept wireframe showed “A1 assigned to C2” on the opening screen while also saying no preset result may ever be shown. Here the chart shows only candidate routes until a method has run.
  2. The zone chart is exact, not decorative. I solved for positions where straight-line distance equals the scenario's travel time, one grid unit per minute. Both scenarios have an exact solution (checked against all travel times to 1e-9). The operator can read the trade-off off the picture and no geography is invented.
  3. “Backup risk: 1 zone” became the A1+A2 backup pair. The data has no zones. It has a pair of units that back each other up and a penalty when both leave. That pair is drawn as a shaded sector that turns red when a decision breaks it.
  4. Four screens, not five. The backend has two fixed scenarios and no editable inputs, so a Scenario Setup screen would be a page of disabled controls. The scenario switch lives in the top bar and the inputs are listed under Method & data.
  5. A QAOA result always shows how often it was sampled. All six recorded QAOA runs returned the true optimum as their “best feasible sample”, including one that sampled it less often than random guessing would (8 shots of 1000, against 15.6 expected). With 1000 shots over 64 states, picking the best sample finds the optimum almost regardless of circuit quality. So the result card puts the hit count and the random-guess baseline next to the assignment.
  6. “Why it changed” is a sentence, not a chart. Once two methods have run, the console states what moved: which call got a different unit, how many minutes that cost, and what happened to the coverage penalty.

States every screen must handle

StateWhat the operator sees
No run yetCandidate routes only. Decision panel says no analysis has run. No costs anywhere.
RunningRun button disabled and labelled with the method. QAOA shows its step (optimising, then sampling).
Feasible resultRoutes drawn, held units marked, cost split into response and coverage, validation badge.
QAOA, optimiser not convergedResult stays visible with an amber “did not converge” line quoting the optimiser's message. The recorded p=2 run is a live example.
QAOA, no feasible sampleNo routes, no cost. “No feasible assignment in N shots” with the most frequent bitstring shown as infeasible. The exact answer is never substituted.
Backend errorRed panel with the message, run logged as failed, excluded from every comparison.

Found in the backend while wiring in real data

  • Wrong random baseline for the five-qubit scenario. app/result_adapter.py line 533 hard-codes a uniform feasibility rate of 4/32. Enumerating with the project's own validator gives 10 feasible states of 32. The Quantum Lab compares QAOA against this number, so it currently flatters QAOA. This prototype uses the enumerated value.
  • README figures and app figures disagree. The README reports QAOA p=1, seed 10 hitting the optimum 0.94% of the time. The app's adapter with the same seed gave 6.8% (68 of 1000 shots). I did not rerun the audit script, so I can't say which is stale. Worth reconciling before judges compare the two.

Suggested build order

  1. Backend additions above, with tests. Fix the baseline.
  2. Console screen: top bar, queue, zone chart as inline SVG, decision panel, run ledger.
  3. Quantum Lab and Compare, reusing the existing chart helpers where they fit.
  4. Method & data page, moving the long disclaimers out of the other screens.
  5. Browser pass at 1280 px and 400 px, then the demo script: run nearest-available, run exact, read the “why it changed” line, open QAOA.
